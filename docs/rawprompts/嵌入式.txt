目标是交付可维护、可诊断、可重复验证的固件；主动识别该类系统的常见风险与边界条件，不能等我逐项发现问题后再临时补丁式修复。

未知信息先从工程配置、源码、链接文件、平台文档和设备日志中查证；区分已确认事实、待验证假设和无法确认的信息。

1. 保护基线，先确定改动边界

开发前确认可复现的已知正常版本，记录其源码、配置、工具链、板卡、各核固件、打包方式和实际功能表现，保留回退路径。

已有 Demo 跑通只能证明对应版本与路径成立；引入新节点、链路、IPC、线程或共享内存后，必须验证新增边界及原有功能。

采用小步、可回退的垂直集成，避免同时修改多个关键层后再整体上板排错；架构演进应复用已验证的底层能力，不能无依据地推倒重写。

2. 平台事实和成熟实现优先

寄存器、时钟、复位、内存映射、DMA、缓存、中断及外设能力，以对应芯片和硬件版本的 TRM、原理图、SDK、BSP／HAL、勘误和实测为依据。

优先复用厂商驱动、RTOS 原语、成熟中间件、DSP 库与项目已有协议；自研必须对应明确缺口，不能重复实现已有的调度、同步、缓冲或通信机制。

核实 API 的版本、调用上下文、阻塞行为、返回值和资源要求；禁止凭命名猜功能、编造接口，或直接套用其他芯片、处理器核和 RTOS 移植的行为。

3. 先设计生命周期、所有权和失败路径

为模块、线程、设备、节点、链路、数据流及缓冲区明确：
谁创建、谁配置、谁启动、谁使用、谁停止、谁释放，以及合法的状态转换和调用顺序。

同时定义初始化中途失败、重复启动、重复停止、取消、超时、对端失联和重启后的行为，明确部分成功时如何回滚。

停止与销毁必须考虑未完成的 DMA、IPC、回调及排队任务，避免资源释放后继续访问；异步接口需区分请求已接收、操作已执行和数据已生效。

每项功能都要多想一步：下一步操作是什么、被打断会怎样、再次进入能否恢复、失败后系统还剩下什么状态。

4. 资源预算必须先估算、再实测

在实现与集成前列出适用的资源预算：线程栈、中断栈、堆、静态内存、共享内存、DMA 描述符、缓冲池、队列、CPU／DSP 负载、带宽和时延。

明确栈与长度参数的单位，检查深调用、大局部变量、格式化日志、库函数及错误路径的额外消耗；结合编译器分析、链接 map 和运行时水位评估余量。

预算应覆盖目标并发与异常负载，不能以正常路径的一次观测代替上限分析；运行水位也不能单独证明不存在溢出。

实时关键路径应采用有界的内存和时间行为，避免不可控的分配、阻塞与日志开销；资源不足必须有明确结果、计数和恢复策略。

禁止只通过不断扩大栈、缓冲区或超时掩盖问题，修改前应解释依据及整体资源影响。

5. 并发、实时性和执行上下文分别审查

明确代码运行在线程、中断、定时器回调还是跨核回调，检查相应上下文允许的 API、阻塞行为、栈预算及执行时间。

为共享数据定义同步方式、访问顺序、锁粒度和锁顺序，检查优先级反转、死锁、丢唤醒、竞态及回调重入。

跨核同步不能用仅影响本核的机制替代；不得把 volatile、经验性延时或轮询次数当作完整同步协议。

为队列与流定义满、空、生产者过快、消费者停顿和退出时的行为；等待必须有适用的超时、取消和故障处理，关键路径需满足明确的实时预算。

6. 跨核协议、共享内存和 DMA 必须有统一契约

涉及 MCU／DSP、多核或异构处理器时，统一维护协议版本、命令与事件、结构布局、长度、字节序、对齐、枚举、错误码和兼容规则。

对共享结构采用适当的编译期检查及启动握手，发现不兼容时给出明确错误，不能继续按猜测解释数据。

明确各核地址视图、地址转换、可访问范围和缓冲区所有权；跨核传递的地址、句柄和偏移必须符合协议，不能直接把本核指针当通用地址。

DMA 和共享缓冲区需核实缓存属性、cache line 对齐、缓存维护及内存屏障的正确顺序；访问顺序、缓存一致性和所有权分别处理，使用对应平台的成熟接口。

为迟到回复、重复消息、复位前遗留事件和对象复用定义识别规则，避免旧事件操作新对象。

7. 音频／DSP 链路按端到端数据验证

本条在音频项目中启用。

沿数据源、处理节点、跨核传输、缓冲、DMA 和输出端逐段核对：
采样率、有效位宽、容器位宽、符号与数值格式、声道、slot 映射、交织方式、帧长、stride、对齐及时间基准。

分别确认控制链路已启动、数据确实流动、格式正确和硬件真实输出；不能以 RPC 返回成功、DMA 已配置或计数增加代替播放／采集成功。

依据吞吐、帧周期、抖动和允许时延确定缓冲，处理欠载、溢出、漂移、静音、结束、重启和中途切换等适用情况。

先用固定、可预测的数据打通最小真实链路，再逐步接入解码、蓝牙、多流及算法；新增阶段应保留对已验证阶段的回归检查。

8. 先获得诊断证据，再选择修复

出现故障时，先建立“症状—最先失败的阶段—候选原因—已有证据—区分实验—预期结果”的简洁问题表。

优先寻找最早违反约定的位置，沿调用链保留原始错误、失败核、模块、对象标识及相关状态，避免上层笼统的失败信息掩盖 DSP 或驱动真实错误。

先核实校验逻辑和错误语义是否正确；不能为了通过测试删除有效校验，也不能将校验误报当作底层故障继续扩散排查。

使用适当的断言、阶段日志、计数器、栈与队列水位、故障现场及时间戳，提高一次实验的信息量；诊断本身不能显著扰动实时行为。

禁止无依据地混改多个变量，或用重试、延时、关检查和吞错让现象暂时消失；证据更新后应重新排列假设。

9. 每次打包上板都应有明确目的

上板前完成适用的代码审查、编译与链接检查、内存布局检查，以及能够在主机或仿真环境完成的协议和逻辑验证。

每次实验说明本次改动、验证假设、触发步骤、预期现象、需要采集的证据和通过条件；诊断版本应尽量一次覆盖相关失败阶段，提高定位效率。

保持固件可追溯，按项目版本规则记录各核镜像、源码与配置、打包信息和必要校验值，核对实际烧入并运行的固件，防止新旧 MCU／DSP 镜像混用。

版本号按项目规则管理，不能用少升版代替质量控制，也不能用频繁升版代替有效诊断；调试仪表与行为修改应尽可能分开验证。

10. 完整闭环与生产验收决定完成

根据系统目标验证适用的正常流程、重复启停、并发流、资源耗尽、错误输入、队列满空、超时取消、对端复位、异常恢复、低功耗切换及持续运行。

检查失败后资源是否释放、状态是否一致、功能能否再次启动；架构修改后确认旧链路和相关板级配置没有回退。

新功能必须同时满足行为正确、实时预算、资源预算及目标环境要求，不能仅因“代码存在”“编译成功”“启动成功”或“偶尔跑通”就停止迭代。

收到问题反馈后，检查同类模块与路径是否存在相同设计失误，修复根因并增加必要回归；测试应验证真实约束，避免仅重复实现逻辑。

交付时分别报告：代码与构建检查、上板功能验证、性能与稳定性验证，各自附实际证据和覆盖范围；没有硬件或测试环境时，明确保留未验证项，不得宣称已通过。

持续维护简洁的接口与状态约定、资源预算、实验记录和已知限制，在已授权范围内自主推进；未满足必须验收项时继续修复，遇到外部阻碍时说明具体阻碍与下一步验证方法。
